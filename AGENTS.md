# mirror / 观己 — Agent Guide

## Product direction

- Chinese MBTI-style self-exploration site, designed for WeChat mobile first and adapted to PC, with a full English site under `/en` that shares every layout and is paid in USDT/USDC (`PRICE_USD_CENTS`, default $1).
- Visual system is fixed: cool gray paper `#edf2f3`, near-black ink `#171b1c`, black editorial report `#121718`, warm accent `#c49473`, thin radar chart, pill-shaped primary actions, Manrope for Latin + system CJK fonts.
- Brand artwork uses the facing mirror contours and warm centre dot in `src/components/brand/brand-logo.tsx`; the outlined lockup is shared by the header and OG images and follows the locale: `mirror / 观己` (viewBox 194) in Chinese, `mirror / look within` (Manrope 500, 13px; viewBox 232) in English. Pass `locale` to `BrandLogo` and size OG logos with `brandLogoWidth(locale, zhWidth)` so both lockups keep one glyph scale. Phone headers (under 721px) show only the mark and `mirror` wordmark, identical in both languages: `BrandLogo tagline={false}` at `brandLogoWidth(locale, 168, false)`, the glyph scale of the 168px Chinese lockup; never put 观己 or look within back on phones. Desktop headers keep the full lockup at 194px in Chinese and 232px in English. `app/global-not-found.tsx` sits outside `[lang]` and follows the same rule with the Chinese lockup. Run `npm run brand:build` after artwork changes to refresh `public/assets/brand/`, `src/app/favicon.ico` and `docs/brand/logo-preview.png`; see `docs/brand/README.md` for variants.
- The reference screenshots in `docs/design-evidence/` are the source of truth for layout, density, spacing and copy. Do not change copy strings, pixel values or colors without a matching screenshot or explicit user request.
- The home hero keeps text legible over the portrait without dimming the rest of the photo (user request, 2026-09-15). Phones: a paper scrim behind the copy (solid at the photo's 220px top edge, 82% under the last line, fading out over 120px) and a paper fade behind the fixed dock, whose price and sample link are both slate `#52656e`. Desktop: the two captions are paper-coloured over a 160px ink fade at the photo's foot. Each language has its own portrait: `src/assets/portrait.jpg` (English) and `src/assets/portrait-zh.jpg` (Chinese; Pexels 3754248, its warm wall regraded to the paper tone so the background matches the page — see `docs/brand/README.md`). `pageMessages.home.portraitAlt` describes each, and the home OG card reads the same file through `portraitDataUrl(locale)`. Recheck WeChat height 390×749 and English copy (four description lines) after changing either portrait or the hero copy.
- The paid report price is `PRICE_FEN` (default ¥6.9) / `PRICE_USD_CENTS` (default $6.9). **Nothing before the test may quote a price or hint that anything is sold** (owner decision, 2026-09-17). Home, quiz, `/result/sample`, `/report/sample`, `/about`, `/preferences`, `/types` and both `llms` files say the test is free and stop there — no amount, and no 付费 / 解锁 / 订阅 / 续费 / paid / unlock / subscription. The home JSON-LD keeps only the free Offer and the sample `Product` has none, because the pages no longer show a paid one; `site.description` (every page's meta) says only that the test is free. The amount lives on the purchase surfaces alone: the result page's unlock dock and `UnlockPanel`, `PaymentSheet` and `/pay/[orderId]`, all of which a visitor reaches only after finishing a test. `/help`, `/terms` and `/privacy` still describe payment in full — they inform buyers rather than sell. `tests/e2e/flow.spec.ts` asserts the home and sample bodies match none of those words. In `mock` payment mode every "演示" label must stay; in `wechat` mode they switch to real payment copy. Never present the client-side `unlocked` flag as authorization: `/report/[id]` decides on the server.

## Stack rules

- Next.js 16 App Router with `cacheComponents: true`. Anything that reads `cookies()`, `headers()`, `params`, `searchParams`, `usePathname()`, `useSearchParams()` or does uncached I/O must sit under a `<Suspense>` boundary or a `loading.tsx`. Route handlers that must never be prerendered call `await connection()` first.
- `src/proxy.ts` (not middleware) issues the signed `mid` visitor cookie. Sign/verify lives in `src/lib/visitor-token.ts`; server code reads it through `src/lib/session.ts`.
- Locales: every page lives under `src/app/[lang]` with the root layout there (`next/root-params` `lang()`; `generateStaticParams` from `publishedLocales` in `src/lib/i18n/locale.ts`). Chinese keeps unprefixed URLs: the proxy rewrites `/x` to `/zh/x` and 308-redirects a typed `/zh/x`; `/en/x` passes through. Route handlers, `robots`, `sitemap`, the Chinese `manifest`, root `llms*.txt`, `favicon` and the Chinese root `opengraph-image` stay at the app root and in the proxy's `ROOT_ROUTES`. Each language installs as its own app: `src/lib/manifest.ts` builds both, `app/manifest.ts` serves the Chinese one and `app/[lang]/manifest.webmanifest` the English one, and the `[lang]` layout sets `manifest: href(locale, "/manifest.webmanifest")` so the root link never ships Chinese to `/en`. Unmatched URLs under a language prefix hit `app/[lang]/[...rest]/page.tsx`, whose only job is to call `notFound()` so `[lang]/not-found.tsx` answers in that language; `app/global-not-found.tsx` is the backstop for paths outside `[lang]`. A 404 is a non-streamed response, so every `notFound()` in the app returns the shell and resumes its copy on the client — assert 404 copy through a rendered page, never the raw HTML. Build every internal link with `href(locale, path)`; never hard-code `/quiz`. The language switch is `site/language-menu.tsx`, a Radix dropdown in `AppHeader` (globe + language name at the end of the desktop nav, short code beside the phone 更多 menu) whose options are plain `<a hrefLang>` links resolved on the server; the current language is checked and not a link. Pass `path` for pages that exist in both languages so each option opens the same page; omit it on language-bound pages (real results, reports, orders, 404), where it opens the other home. Do not derive it from `usePathname()`. Options render only while the menu is open, so the head's hreflang alternates stay the crawler path. The menu fades in over 160ms and the caret turns; both stop for reduced motion.
- Header navigation replaces footers: no page renders a footer or a bottom list of links. From 721px `AppHeader` shows 人格测试 · 我的报告 · 更多信息 · language; phones show only the language code and 更多, whose menu starts with 人格测试 and 我的报告 (a third phone item overflows at 360–375px or shrinks the logos). The phone logo or back link, language code and 更多 share one centre line, as in `docs/design-evidence/mobile-home.png`: keep each label `items-center` in its 44px tap box and never top-align one (a link with `min-h-11` and no flex centring puts its text at the top). Both menus then list 了解四维偏好, 16 型人格, 测试说明, 测试与订单帮助, and after a rule 隐私政策 and 用户协议 (`moreGroups` in `app-header.tsx`). `site/more-menu.tsx` is a disclosure button (`aria-expanded`, `aria-controls`) over a panel of server-rendered links that is only `hidden` while closed, so the links stay in the HTML; unlike the language options they have no other crawler path, so never move them into a render-on-open dropdown. Do not use `<details>`: its implicit `group` role would sit on every page and collide with the quiz answer group that tests find by role. The panel closes on an outside press, Escape (focus returns to the button), focus leaving or a followed link, and opening sends `more_menu_open`. The panel reuses the language menu's card, 160ms entrance and caret turn, all off for reduced motion. The about sheet now opens only from the desktop home steps bar; `/about` serves everyone else. `tests/e2e/header-nav.spec.ts` covers the HTML links, closing, the 360px phone fit and the phone header's centre line.
- Copy: page and component strings live in `src/lib/i18n/messages/*` as `{ zh, en }` with `en: typeof zh`, so a missing key fails typecheck; Chinese strings stay verbatim. Server Components read the locale with `getLocale()`; client islands with `useLocale()` (the root layout's `LocaleProvider`). Content modules (`site`, `personality`, `type-context`, `preference-content`, `report-content`, `llms`) take a `locale` that defaults to `zh` and must keep Chinese output unchanged. English type names are the four preference labels (`Introverted · Intuitive · Feeling · Judging`) — never 16Personalities-style nicknames — and English copy says MBTI®-style / not the official MBTI® instrument.
- No English decorative copy on Chinese pages (user request, 2026-09-16). Eyebrows, photo captions, report chapter labels (第一章 / `CHAPTER 01`) and OG kickers are Chinese in `zh` and English in `en`, so every such string lives in `src/lib/i18n/messages/*` — never hard-code one in JSX, and never pair the two languages in one string (`SAMPLE REPORT · 示例报告`). Only MBTI, type codes, dimension letters and the `mirror` wordmark stay Latin. The mirror rule holds for English pages: no Chinese fallbacks, including accessible names such as `ResponsiveSheet`'s close label. `app/global-not-found.tsx` is the one exception — it sits outside `[lang]`, cannot know the language, and keeps its one English line under the Chinese copy.
- A result's language is its questionnaire's (`questionnaireLocale`): `en32-v1` / `en64-v1` mirror `legacy32-v1` / `standard64-v1` item for item (dimension and reverse flags copied, text only differs). `/result/[id]`, `/report/[id]` and `/pay/[orderId]` redirect to that locale; orders take price, currency (`CNY` fen / `USD` cents), provider and messages from it. API messages that precede a known result use `requestLocale()` (same-origin `Referer`).
- `/my/report` renders every result owned by the signed visitor, newest first, including unpaid summaries. Never infer history from localStorage. Full order numbers are bearer recovery credentials: `POST /api/reports/recover` restores the order's visitor cookie for any order status, but never unlocks a result. Keep order numbers owner-only, the same-origin check, database-backed rate limit, and fresh navigation after recovery; the proxy must not overwrite this response's restored cookie.
- Tailwind v4 with tokens in `src/app/globals.css` (`@theme`). Breakpoints are `md` = 721px, `xl` = 1101px, `2xl` = 1450px to mirror the prototype's media queries. Mobile-first: base classes are the phone layout, `md:` is desktop. Use arbitrary values for exact prototype numbers (`text-[10px] tracking-[.14em]`). Shared patterns are `@utility` (`eyebrow`, `pill`, `text-link`, `back-button`, `pb-safe-4`).
- Light pill buttons keep a light background on hover (`paper` / `#edf2f3`) so their ink text stays readable in dark CTA sections; never inherit the dark pill hover fill.
- Motion is restrained and finite: home title lines enter 90ms apart, the portrait settles from 1.025× in 1.1s, and report chapters enter in 280ms. Keep CTAs and fixed docks outside animated ancestors. Radar SVG and data stay server-rendered; its small client shell only coordinates a single 720ms reveal per mounted chart, including when scrolled into view. Preserve the complete static fallback, respect reduced motion, and never replay a finished chart merely because a chapter becomes visible again.
- Interaction motion: question content enters from ±8px over 240ms, with direction shared by next/back/review navigation; answers never auto-advance. Press/check feedback lasts 160ms. The strengths switch moves its background in 240ms and fades the visible list in 200ms, retaining both server-rendered lists. Desktop dialogs use a stationary fading overlay and a 240ms entrance / 180ms exit; let Radix manage presence and Vaul manage phone drawer gestures. Disable these animations for reduced motion, and limit hover movement to fine pointers.
- Quiz counters use `NumberMotion`: only changed digits roll for 240ms, increasing upward and decreasing downward. Accessible text always exposes the latest number once; decorative old digits are hidden for reduced motion and print. Do not count through intermediate values or queue transitions. Carry the old total across the version picker so 32/64 changes animate without merging drafts. Version-card copy enters in 280ms with a 60ms offset for the second card; its CTA stays outside the animation. Quiz progress settles in 360ms; accordion content opens/closes in 240/200ms using Radix's measured height.
- shadcn/ui primitives live in `src/components/ui/*` and are restyled to the prototype; add new ones with `npx shadcn@latest add <name>` then restyle. Icons come from `@phosphor-icons/react` (`/dist/ssr` in Server Components).
- Client islands are small and explicit: `quiz/quiz.tsx`, `result/result-actions.tsx`, `payment/*`, `report/chapter-ui.tsx`, `site/site-overlays.tsx`, `site/language-menu.tsx`, `site/more-menu.tsx`, `analytics/page-views.tsx`, `analytics/track-view.tsx`. Prefer `useSyncExternalStore` over `setState` in effects (the React Compiler lint rule is an error).
- Page content must be in the server HTML. The report is the case to watch: `report/report-body.tsx` is a Server Component that renders **all four chapters plus both the strengths and the blind-spot lists**, and `report/chapter-ui.tsx` only toggles which one is visible. Never move chapter content back into a client component — a JS-free reader must see the whole report. `tests/e2e/flow.spec.ts` asserts this against the raw HTML.
- **The sample is the real page with sample data — never a second layout.** `/result/sample` is the result page and `/report/sample` is `ReportBody`, the same component a paying reader gets. Do not add a sample-only reading view, and do not embed the report into the result page; if the sample needs something, add it as chrome (`report/sample-notice.tsx`, `result/sample-cta.tsx`) around the shared layout. `tests/e2e/flow.spec.ts` asserts both pages expose the same four chapter panels and switcher.
- Say it is a sample, everywhere: page title, the 示例报告 notice above the reading, the sidebar badge and the phone heading row all read 示例报告 when `data.sample` (`SAMPLE REPORT` in English).
- The desktop report sidebar uses a stretched grid cell with a sticky inner wrapper. Keep its sticky range within the report reading row so it stops before the full-width closing CTA or footer.
- The sample sells the test, not the report. The notice link, the last chapter's closing link, `SampleCta` and the phone dock all point at `/quiz`; its body and footnote invite the test and never mention buying anything. Never render `UnlockPanel`, an unlock button or a hero price on a sample — nothing there is for sale. `ResultActions` and `PaymentSheet` are for real results only and are not mounted on the sample.
- The active chapter is derived from `?chapter=` by `report/chapter-store.ts` (a `useSyncExternalStore` over `history`), not from `useSearchParams`, so the page stays statically prerenderable. The trade-off: a deep link like `?chapter=3` paints chapter 01 until hydration swaps it. Do not "fix" that with an inline script — it fights hydration and costs the static HTML.
- Data access: `src/lib/results.ts`, `src/lib/orders.ts`, `src/lib/visitors.ts` on top of Drizzle (`src/db`). Schema changes go through `npm run db:generate` and commit the SQL under `drizzle/`.
- Questionnaire definitions live in `src/lib/questionnaires.ts`: immutable `legacy32-v1` (32 items) and `standard64-v1` (64 items), balanced by dimension and reverse scoring. Persist question IDs, version, fixed question order, scoring version and report version; changed items require a new version. Keep the original 32-item numeric API and browser drafts compatible. Each version has its own draft; memory fallback must allow completing the current quiz when localStorage fails. Keep manual next, answer review and a confirmed restart of only the current version.
- Quiz shows exactly one previous/next navigation: the fixed dock on phones and the inline navigation from 721px up. Keep both sets on the same answer/progress handlers, allow buttons to shrink on narrow screens, and verify the dock stays inside the viewport before and after scrolling.
- Four dimensions all at or below 60% means unclear: use `profileMeta` / `publicProfile`, show no determinate type, explain both poles, and reject new orders on the server with `UNCLEAR_RESULT`. The 60% threshold is a display convention, not validated confidence. Never remove access to an existing paid report. Paid content uses strength, near-balance, contextual examples and seven days of practice; retain all content in server HTML. Neither questionnaire is a validated or official MBTI instrument; 96-item and A/B versions await user trials.
- SEO/GEO: indexable pages build metadata with `pageMetadata({ locale, path })` from `src/lib/seo.ts` — Next merges `openGraph`/`twitter` shallowly, so a hand-written partial OG object drops siteName, locale and url. It prefixes canonical/OG URLs, emits `zh-CN`/`en`/`x-default` hreflang pairs, and always names the share image explicitly (`image` for segment images) so file-based images never resolve under the internal `/zh` path. The sitemap lists each page per published locale with alternates; `robots.ts` disallows private routes under every locale prefix; English llms files live at `/en/llms*.txt`. Bump `contentUpdatedAt` there with public copy changes (sitemap and `dateModified` read it). `/llms.txt` and `/llms-full.txt` are generated by `src/lib/llms.ts` from the same copy the pages render; never hand-write them or list private routes (`/my`, `/pay`, `/api`, real results). Type pages use the type code as H1 and open the context section with a self-contained “XXXX 是什么意思？” definition from `typeContext().definition`. JSON-LD must describe only visible facts, in the language of the page carrying it: `organizationJsonLd`/`websiteJsonLd` in the `[lang]` layout take the locale, and `websiteId(url, locale)` gives each language version its own `WebSite` node (`#website` / `#website-en`) so the two cannot overwrite each other. The organization is one entity — one `@id`, one `url`, one logo — with only its name and its `contactPoint.url` following the page. Build absolute JSON-LD URLs with `absoluteUrl(baseUrl, locale, path)`. `tests/e2e/i18n.spec.ts` asserts no English page renders a CJK character anywhere, including the flight payload, so a Chinese string reaching a client island fails there. `robots.ts` keeps one `*` group so AI answer crawlers can cite public pages; a bot-specific group would need to repeat every disallow.
- Public support email is configured once in `site.supportEmail` and linked from `/help`, privacy and terms. Home visibly says MBTI 测试体验; `/preferences` explains scores and retesting. Preserve the shared brand artwork, colors and sample/paid page architecture when expanding these flows.
- Payments: `src/lib/payments/index.ts` resolves a provider per mode — Chinese orders use `PAYMENT_PROVIDER` (mock | wechat), English orders `EN_PAYMENT_PROVIDER` (mock | crypto | waffo) — and `refreshOrder` always queries the provider stored on the order. One provider is active per language, so `waffo` replaces the crypto checkout on `/en` rather than sitting beside it. The WeChat adapter is self-contained under `src/lib/payments/wechat/` (Node `crypto` only). Keep `crypto.ts` pure so it stays unit-testable. In mock mode English copy keeps its visible “Demo” labels, like 演示.
- Card payments (`src/lib/payments/waffo/`) go through Waffo Pancake, the merchant of record for English orders: `createPayment` locks a checkout session priced from `PRICE_USD_CENTS` (tax added on top, so the callback’s `subtotal` is what we charged) and returns a `redirect` payload; the buyer leaves for the hosted checkout and returns to `/en/pay/[orderId]`. Never build a card form on-site — that would pull the app into PCI scope. `/api/payments/waffo/webhook` verifies the RSA signature over the **raw** body, stores the event as `<eventType>:<eventId>` for idempotency and drops the buyer’s email before storing. **There is no refund flow** (owner decision, 2026-09-17): refund events are recorded and never revoke a report, and the sheet, terms and privacy policy say up front that purchases are final. A callback or poll that lands after the order expired still unlocks it — the card was already charged.
- Crypto payments (`src/lib/payments/crypto/`, viem + `@solana/kit`, both MIT; no gateway and no WalletConnect/Reown, whose licenses are not open source) pay the configured receivers directly and are read back from the chains. Invariants: Solana orders carry a unique Solana Pay `reference` and pay when a successful transaction referencing it raises the receiver's USDC/USDT balance by at least the price; Ethereum orders pay only from the wallet that signed the order's challenge (`POST /api/orders/[id]/payer`, set once, verified via the RPC so smart wallets work), counting accepted-token `Transfer` logs from `start_block` with `ETHEREUM_CONFIRMATIONS`. Providers return candidates and `claimPaymentEvent` (unique `payment_events.event_id`) lets one transfer pay one order only. Crypto orders last 30 minutes, are checked before expiring and for 24 hours after, and chain reads are throttled per order. Keep matching logic pure (`amounts.ts`, `solana-pay.ts`, `ethereum.ts`) with unit tests. Wallet deep links carry only the public page URL — never an order number — and buyers restore the test in the wallet browser with the recovery form.
- Analytics is GA4, started before hydration by `src/instrumentation-client.ts` → `src/lib/analytics/track.ts` (gtag queue, ads consent denied, Google signals off, `send_page_view: false`, gtag.js loaded after `load`). `NEXT_PUBLIC_GA_MEASUREMENT_ID` is inlined at build time; without it events only queue in `window.dataLayer`, which the e2e tests read. `analytics/page-views.tsx` sends one `page_view` per pathname (not per `?chapter=` / `?unlock=1`), `analytics/track-view.tsx` records views from Server Components, and every other event is typed in `src/lib/analytics/events.ts` and documented in `docs/analytics.md` — add new events to both. Server-rendered CTAs spread `trackAttrs(cta, location)` and a delegated listener sends `cta_click`, so tracking never turns a Server Component into a client one. Privacy invariants: `page_location` / `page_referrer` pass through `sanitizeLocation` / `sanitizeReferrer`, which replace result IDs and order numbers and keep only attribution parameters; `purchase` uses a one-way hash as `transaction_id`; never send answers, scores, personality types, order numbers, openids, wallet addresses or transaction hashes — the privacy policy promises results are not shared. Update the privacy policy when the data sent changes.
- OG images render with satori; fonts are the TTFs in `src/fonts/`. After changing Chinese copy that appears in OG images, run `node scripts/build-og-fonts.mjs` to refresh the CJK subset.

## Sharing and comparison invariants

- P0 single-person sharing stays free. New pairing uses `paid-pair-v2`: both signed visitors must have unlocked the exact results used, including previously purchased results. `legacy-free-v1` guides retain original reading/withdrawal rights; old invitations accept no new participants. Payment never substitutes for either separate consent (`compare-host-v2` / `compare-guest-v2`).
- Invitations may be created directly from a paid result with no parent share. Owner pages expose result/report/management entry points; no hidden P0 card is created. Server continuations save only intent and survive payment/identity recovery; multiple invitations require an explicit choice. A paid order with missing result access offers reconciliation, never a second purchase. Keep the success actions when a dialog becomes a phone drawer.
- The paid report's top invitation card is compact; pending pairing continuations sit after the report reading so its title remains on the first screen. The relationship chapter also has an invitation entry outside its animated content. English phone chapter labels wrap within their four columns, retaining full accessible names; Chinese labels keep their existing layout.
- Public `/pairing`, invitation metadata/copy, and invitations seen before testing introduce value without purchase language. On an owned result and before payment, clearly explain that both people unlock their chosen reports. This follows the latest pre-test product rule. Pairing produces frozen communication prompts; never a relationship score.
- A pair guide is `compare-v3` (`src/lib/compare-content.ts`): one emphasis (the dimension worth saying first, with the single quote the reading is built around), **one card per dimension** in `COMPARE_DIMENSION_ORDER` carrying that dimension's relation, body and a concrete scene, then one shared practice. Every consented category reaches the reading, so the four categories a partner brings produce 81 distinct readings rather than varying only the emphasised one — `tests/unit/compare-content.test.ts` asserts that count, plus role symmetry over all 6,561 pairs. Output stays role-neutral ("一方 / 另一方") because the two readers share one row; who is who is presentation, passed to `ComparisonReading` as `sides` from the already-visible snapshots. Deepening the guide again needs `compare-v4`: `ComparisonReading` renders stored `compare-v1` and `compare-v2` through their own `sections` path and never re-renders them as a v3 reading. The consent versions (`compare-host-v2` / `compare-guest-v2`) do not move with the content version — the scope they cover is unchanged.
- The fictional example (`PairingExample`, on `/pairing`, `/t/[token]` and the result-page benefit) is always a preview: the emphasis plus the one emphasised card and `moreDimensions`, never the four-card reading a pair receives. A free surface must not show the whole paid reading.
- Reader-facing surfaces never print a questionnaire id: `PreferenceSummary` names the version with `questionnaireName()` and `pageMessages.history.version`, as every other page does. The consent scope it shows (four categories, questionnaire version, test date) stays complete but compact, and on `/compare/[id]` it follows the reading so the emphasis leads the page.
- `/t/[token]` has its own OG card (`src/lib/og/invitation-image.tsx`), because a forwarded invitation otherwise previews as the generic home image. It renders only invitation copy — link previews are fetched and cached by third-party servers, so no host categories, dates or tokens belong in it. Its Chinese copy is in the OG font subset (`scripts/build-og-fonts.mjs` reads the compare and pairing message modules); re-run that script after changing it.
- `/s/[token]` reads only the immutable public snapshot. Optional type/dimension fields are omitted when disabled; never pass result IDs, candidate IDs, scores, orders or visitor IDs to public output. Tokens use 24 random bytes; owner mutation still requires the signed visitor.
- `/t/[token]` has separate host consent for four qualitative categories, questionnaire version and test date. `/compare/[id]` is readable only by its two signed visitors. Lock mutation ancestors in share → invitation → pair order; expiry prevents new joining, withdrawal invalidates existing access.
- First-result referral updates run in a nested transaction/savepoint. An analytics SQL error must not abort the result transaction or allow a later retest to claim the missed first result.
- New sharing pages keep complete server-rendered content. `StaticStreamFallback` exposes only containers marked `data-share-static` when JavaScript is disabled; its rules belong to Tailwind's base layer so `[hidden]` reset priority cannot suppress the fallback. It changes presentation only after server authorization.
- Sharing motion is a finite WAAPI enhancement over the visible final state, with no CTA/dock inside animated content. Tests wait for the actual animation start and completion, including reduced-motion changes and print.
- PNG uses an explicit flex-column wrapper (Satori Fragment children do not inherit browser layout semantics). Verify actual PNG layout and decode its QR after changes, not just HTTP status or image dimensions.
- Capability routes redact URL parameters and disable Google collection; first-party sharing events do not mean a message was actually sent. WeChat SDK sharing remains off unless `WECHAT_SHARE_ENABLED=true` after channel verification.
